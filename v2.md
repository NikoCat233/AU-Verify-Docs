# AU-Verify v2 API

The v2 API verifies control of an Among Us account through a friend request. The player does not need to add custom regions to their game client. The API is available under `/v2/api`.

Use an API key issued by the service operator. Send it in the `Authorization: Bearer <api-key>` header. Do not put API keys in URLs or request bodies. Replace `https://verify.example.com` in the examples with the service's API origin. Our provided origin is `https://au-verify.niko233.top` and we expect requests to go through `https://au-verify.niko233.top/v2/api/{path}`.

## Verification flow

1. Ask the player for the friend code shown by their own Among Us account. The player must provide a usable friend code before verification can start; the API cannot discover a target account without it.
2. Create a verification with `POST /v2/api/verifications`, providing the player's friend code. The precheck validates the friend code and confirms that the target can proceed with friend-request verification.
3. Give the player the returned `addFriendCode`. Your service or bot should retain the returned `verificationId`; it is the identifier your integration uses to track this verification.
4. The player sends a friend request from their Among Us account to the provided friend code.
5. The service checks for the request in the background about once every five seconds. When it detects the player's verification request, it automatically rejects the request and marks the verification as finished.
6. You can ask the player to confirm manually when verification is complete, or poll `GET /v2/api/verifications/{verificationId}` yourself using the saved `verificationId`. We recommend polling every 10 seconds. Read the result when the status changes to `finished`.
7. Optionally use the same `verificationId` with `DELETE /v2/api/verifications/{verificationId}` to hide the verification after use.

## Limitations

- The API does not obtain or return the player's real IP address. Audit records concern the API caller's connection, not the player in the game.
- The flow cannot verify an account when its friend-code feature is disabled or the player cannot provide a usable friend code. Ask the player to provide their own friend code first; do not substitute a guessed or placeholder code.
- The target account must have room for another friend and be able to receive a friend request. A full friend list or full incoming friend-request list prevents verification from starting; the API reports these capacity errors separately.
- A finished verification proves control of the target account at the time the matching request was observed. The caller decides whether the linked-account providers meet its own policy.

## Common API rules

- All endpoints use the `/v2/api` prefix and require a valid Bearer API key.
- Requests and responses use JSON. POST create accepts a JSON object. GET and DELETE have no body.
- Responses containing verification data use `Cache-Control: no-store`.
- Friend codes are trimmed and normalized to lowercase. Times are UTC ISO 8601 strings.
- Verification IDs are UUID v4 values.
- The API caller receives and retains `verificationId` to track its own verification. The player only needs the `addFriendCode` to send the friend request.
- A verification belongs to the API key that created it. Unknown IDs, IDs owned by another key, hidden IDs, and IDs past their visibility deadline all return the same `404 VERIFICATION_NOT_FOUND` response.
- The default challenge window is ten minutes. The caller's polling does not extend it.
- Pending and expired responses never contain PUID, linked accounts, or other account information.
- Only a finished response contains `result`. Without the key's `accountid:read` permission, every `accounts[*].account_id` is present as `null`; all other account fields and records remain present.

## Endpoints

| Method | Path | Purpose | Success |
| --- | --- | --- | --- |
| POST | `/v2/api/verifications` | Precheck a target and create a challenge | `201 Created` |
| GET | `/v2/api/verifications/{verificationId}` | Read a visible challenge or terminal result | `200 OK` |
| DELETE | `/v2/api/verifications/{verificationId}` | Hide a challenge from its owner | `200 OK` |

### Create a verification

`POST /v2/api/verifications`

```http
POST /v2/api/verifications HTTP/1.1
Host: verify.example.com
Authorization: Bearer YOUR_API_KEY
Content-Type: application/json

{"friendCode":"player#1234"}
```

The service trims surrounding whitespace and lowercases the supplied friend code, then always performs a fresh capacity precheck before creating the challenge. A string `friendCode` triggers `400 INVALID_FRIEND_CODE` if, after normalization, it is longer than 128 UTF-16 code units, does not contain exactly one `#`, has an empty username or discriminator, or contains whitespace or control characters. No additional character set or discriminator length is enforced by this API. A missing or non-string `friendCode` is an `INVALID_REQUEST`; a well-formed code with no matching account is a `USER_NOT_FOUND`.

Response: `201 Created`

```json
{
  "verificationId": "f3e40e4b-09bd-4d6c-b4ba-1186b38c39bd",
  "status": "pending",
  "targetFriendCode": "player#1234",
  "addFriendCode": "verifyabcd#5678",
  "createdAt": "2026-10-31T08:00:00.000Z",
  "expiresAt": "2026-10-31T08:10:00.000Z",
  "lastChecked": null,
  "readableUntil": null
}
```

`expiresAt` is ten minutes after challenge creation. Share `addFriendCode` with the player so they can send the friend request.

### Read a verification

`GET /v2/api/verifications/{verificationId}`

```http
GET /v2/api/verifications/f3e40e4b-09bd-4d6c-b4ba-1186b38c39bd HTTP/1.1
Host: verify.example.com
Authorization: Bearer YOUR_API_KEY
```

GET does not poll the upstream service, update `lastChecked`, or extend visibility.

#### Pending response: `200 OK`

```json
{
  "verificationId": "f3e40e4b-09bd-4d6c-b4ba-1186b38c39bd",
  "status": "pending",
  "targetFriendCode": "player#1234",
  "addFriendCode": "verifyabcd#5678",
  "createdAt": "2026-10-31T08:00:00.000Z",
  "expiresAt": "2026-10-31T08:10:00.000Z",
  "lastChecked": "2026-10-31T08:00:05.000Z",
  "readableUntil": null
}
```

Pending responses omit `finishedAt`, `result`, PUID, and account data entirely.

#### Finished response: `200 OK`

Finished results are visible for 30 minutes after `finishedAt`. `addFriendCode` is `null` after the challenge is finished.

```json
{
  "verificationId": "f3e40e4b-09bd-4d6c-b4ba-1186b38c39bd",
  "status": "finished",
  "targetFriendCode": "player#1234",
  "addFriendCode": null,
  "createdAt": "2026-10-31T08:00:00.000Z",
  "expiresAt": "2026-10-31T08:10:00.000Z",
  "lastChecked": "2026-10-31T08:02:03.000Z",
  "readableUntil": "2026-10-31T08:32:03.000Z",
  "finishedAt": "2026-10-31T08:02:03.000Z",
  "result": {
    "puid": "target-product-user-id",
    "friendcode": "player#1234",
    "accounts": [
      {
        "account_id": null,
        "provider": "steam",
        "display_name": "Example Player",
        "last_login": "2026-10-31T07:50:00Z"
      }
    ],
    "display_names": ["Example Player"],
    "last_login": "2026-10-31T07:50:00Z"
  }
}
```

The `accountid:read` permission applies independently to every entry in `result.accounts`. When a player has multiple linked accounts, each entry retains its own provider, display name, and last-login value; with permission, each `account_id` contains that entry's linked ID. Without permission, every `accounts[*].account_id` is `null`, while all entries and their other fields remain unchanged. For example, a two-account result without the permission looks like this:

```json
{
  "accounts": [
    { "account_id": null, "provider": "steam", "display_name": "Example Player", "last_login": "2026-10-31T07:50:00Z" },
    { "account_id": null, "provider": "epic", "display_name": "Example Player", "last_login": "2026-10-30T12:00:00Z" }
  ],
  "display_names": ["Example Player"],
  "last_login": "2026-10-31T07:50:00Z"
}
```

With `accountid:read`, those two `account_id` values would instead be the respective linked IDs, for example `"steam-account-id"` and `"epic-account-id"`.

A successful lookup with no linked accounts returns `"accounts": []`, `"display_names": []`, and `"last_login": null`.

#### Expired response: `200 OK`

An unfinished challenge becomes expired at its original `expiresAt`. It remains readable for 30 minutes after that original deadline. `addFriendCode` is `null`; expired responses omit PUID and all account data.

```json
{
  "verificationId": "f3e40e4b-09bd-4d6c-b4ba-1186b38c39bd",
  "status": "expired",
  "targetFriendCode": "player#1234",
  "addFriendCode": null,
  "createdAt": "2026-10-31T08:00:00.000Z",
  "expiresAt": "2026-10-31T08:10:00.000Z",
  "lastChecked": "2026-10-31T08:09:55.000Z",
  "readableUntil": "2026-10-31T08:40:00.000Z"
}
```

At or after `readableUntil`, GET returns `404 VERIFICATION_NOT_FOUND`. Reads never extend either visibility window.

### Delete a verification

`DELETE /v2/api/verifications/{verificationId}` accepts a visible pending, finished, or expired verification. It has no body.

```http
DELETE /v2/api/verifications/f3e40e4b-09bd-4d6c-b4ba-1186b38c39bd HTTP/1.1
Host: verify.example.com
Authorization: Bearer YOUR_API_KEY
```

Response: `200 OK`

```json
{
  "verificationId": "f3e40e4b-09bd-4d6c-b4ba-1186b38c39bd",
  "deleted": true,
  "deletedAt": "2026-10-31T08:03:00.000Z",
  "message": "Verification deleted."
}
```

Delete hides the verification from its owner. Repeated DELETE and subsequent GET return `404 VERIFICATION_NOT_FOUND`.

## Failure responses

Every failure response has the form `{"error":{"code":"...","message":"..."}}`. The tables below show the response body for each documented failure scenario. Unknown JSON properties are ignored; they do not cause `INVALID_REQUEST` when the required fields are valid.

### Create verification failures

| Failure scenario | HTTP response body |
| --- | --- |
| Malformed JSON, non-object body, missing `friendCode`, or a field with the wrong type | `400 {"error":{"code":"INVALID_REQUEST","message":"The request is invalid."}}` |
| Friend code is malformed | `400 {"error":{"code":"INVALID_FRIEND_CODE","message":"The friend code is invalid."}}` |
| No account exists for the friend code | `400 {"error":{"code":"USER_NOT_FOUND","message":"User not found."}}` |
| Target's friends list is full | `400 {"error":{"code":"TARGET_FRIENDS_FULL","message":"The target user's friends list is full."}}` |
| Target's incoming friend-request list is full | `400 {"error":{"code":"TARGET_FRIEND_REQUESTS_FULL","message":"The target user's incoming friend request list is full."}}` |
| Missing, malformed, revoked, or disabled API key | `401 {"error":{"code":"INVALID_API_KEY","message":"A valid API key is required."}}` |
| Wrong path or unsupported HTTP method | `404 {"error":{"code":"ROUTE_NOT_FOUND","message":"API endpoint not found."}}` |
| Request body exceeds the configured limit | `413 {"error":{"code":"PAYLOAD_TOO_LARGE","message":"The request body is too large."}}` |
| Body is sent with a content type other than `application/json` | `415 {"error":{"code":"UNSUPPORTED_MEDIA_TYPE","message":"Content-Type must be application/json."}}` |
| API key exceeds its per-minute request limit | `429 {"error":{"code":"RATE_LIMITED","message":"The request limit has been exceeded. Please try again later."}}` |
| Unexpected internal failure | `500 {"error":{"code":"INTERNAL_SERVER_ERROR","message":"An internal server error occurred."}}` |
| Upstream returns an unexpected or unclassified response | `502 {"error":{"code":"UPSTREAM_ERROR","message":"An upstream service returned an unexpected response."}}` |
| Upstream is unavailable or times out | `503 {"error":{"code":"UPSTREAM_UNAVAILABLE","message":"An upstream service is temporarily unavailable."}}` |
| The precheck cannot safely complete | `503 {"error":{"code":"PRECHECK_UNAVAILABLE","message":"The verification precheck is temporarily unavailable."}}` |
| No challenge identity can be safely issued | `503 {"error":{"code":"SERVICE_UNAVAILABLE","message":"The service is temporarily unavailable."}}` |

Unknown upstream failures are never treated as proof that a user does not exist. Raw upstream error bodies are not returned.
